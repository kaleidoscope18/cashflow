# Cashflow

Ledger application that allows you to know if your account will be overdraft someday.  
All features for this app are described in files under `bdd/features/`.
Developing with a prod database since this is a hobby project.

## Technologies

- Go
- GraphQL
- PostgreSQL
- Supabase

## Structure

Packages:

| Name       | Description                                |
| ---------- | ------------------------------------------ |
| api        | graphql api                                |
| bdd        | bdd tests in gherkin                       |
| dev        | dev tools                                  |
| domain     | business logic                             |
| models     | contracts                                  |
| repository | database layer                             |
| utils      | reusable functions independent from domain |

## Development flow

I develop this app in a TDD way (red-green-refactor), here's how:

- I first write the scenarios I need to code in a `*.feature` file.
- Then I run `gherkingen <feature_file>.feature` to print the tests I need to implement.
- I implement them and the test will be failing first (red).
- I implement the code to make the tests pass (green).
- I improve and refactor the code.
- I add unit tests with AI to speed me up.
- I make sure the tests are not flaky by running the whole test suite many times.

### GraphQL

When changes are made in `.graphqls` files, you will need to regenerate code with graphqlgen by using this command:

```sh
cd api && rm -rf /graph/generated && go run github.com/99designs/gqlgen generate && cd ..
```

- All files under `api/graph/generated` will be regenerated
- If the regeneration throws an error, that means you made a breaking change. Fix these errors and make sure no errors occur when running the above command.

### BDD

BDD testing is in `bdd` package and gherkin natural language is used with `features/*.feature` files.  
They are implemented in normal test files, but generated by `gherkingen`.

```sh
# install gherkingen
go install github.com/hedhyw/gherkingen/v4/cmd/gherkingen@latest

# generate tests
gherkingen <feature_file>.feature
```

## Architecture

The app will follow the DDD project architecture.  
Initial bootstrap is done in `main.go`, which is the entry file.  
It will instantiate the **repository** instances from `repository` package.  
Repositories are injected into the **services** of `domain` package.  
The services are used by **resolvers** (GraphQL) in `api` package.  
All the domain logic is in `domain` package alongside services that use them.  
All domain models are in `models` package.

### api package

Resolvers for each GraphQL mutation and query.
This layer is responsible for validating the input and calling the services.

### domain package

Contains all the business logic and domain rules of the application. This layer is independent of external concerns like databases or APIs. It defines the core behavior and operations through services that orchestrate domain models and enforce business rules. The domain layer should be the most stable part of the application, with changes driven by business requirements rather than technical details.

### models package

Contains all the data structures and interfaces that represent the core domain concepts. These models are used throughout the application layers and define the shape of the data and behavior contracts between different parts of the system. Models should be pure data structures without business logic, which belongs in the domain layer.

### repository package

Handles data persistence and retrieval operations. This layer abstracts the database interactions from the rest of the application, mapping from and to the domain models. It allows the application to remain database-agnostic. The repository layer encapsulates all SQL queries, database connections, and data mapping logic.

### backup of supabase schema

```sh
pg_dump "postgresql://<username>:<password>@<host>:<port>/postgres?sslmode=require" -n cashflow -s -F p > dev/schema_backup.sql
```

## Lessons learned

- We can create modules inside modules.
- Resolvers do validate fields first, then map the values then call the services
- Its not a good idea to use models for the api or repository layers
- Errors should be logged at every layer, but resolver should return a custom error message
- Use channels to validate inputs simultaneously in resolvers.
